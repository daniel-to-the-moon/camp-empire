# 露营者车型图鉴（第一阶段）

出处：issue #31（来源提案 #21；用户 2026-11-07 拍板第一阶段）。代码：`src/shared/dex.ts`（规则与视图）、`src/client/dex.ts`（面板），测试 `tests/dex.test.ts`。

## 做什么

- 左侧面板“车型图鉴 n / 25”按钮打开面板：25 个收集位，按 9 款基础车型分组（`models.json` 共 9 款、25 个高度变体；提案 #21 中“225 个收集位”有误，以 issue #31 更正为准）。
- 点亮规则（明码，无概率抽取、无付费）：
  1. NPC 露营者**入场即算**一次到访（私家车位与爱心车位都算），点亮其车型并累计次数，记首次到访时刻；
  2. 玩家在车库里选用过的变体也点亮（开局默认车也算），只标“你开过”，不计到访。
- 已点亮：车型名、高度、首次到访日期（上海日历）、累计到访次数；未点亮：问号剪影 + 解锁条件。
- 完成度：已点亮 / 25。

## 不做

营地参观、限定涂装 / 道具、排行榜（留待后续讨论）。图鉴只读，不入账、不给奖励。

## 实现口径

- 到访在 `state.ts tick()` 里随 NPC 回放记录，离线回放期间的到访同样计入。
- 幂等：parking_id = `车位#循环序号`，每个车位的循环序号单调递增；`dex.counted[车位]` 记已计入的下一个序号，重复回放、事务重做、重复加载都只计一次。
- 存档兼容（不升存档版本）：`loadSave` 每次加载都调 `reconcileDex` 补算。NPC 车型只由（种子、车位、循环序号）决定（`npc.ts variantForCycle`），所以图鉴加入前已离开的露营者，车型与次数可按种子**精确**回填；但到达时刻依赖当时的侧边帐状态、存档未记录，回填的首次日期显示“升级前，日期未记录”。正停在车位里的露营者按实际到达时刻记。旧版本标签页写过的存档里漏计的到访也会在下次加载时补上。

## 定量：只靠露营者到访集齐 25 款要多久（推演，非新增数值）

每位露营者车型在 25 款中等概率（`variantForCycle`：`floor(u × 25)`，u 均匀）。集齐 n 款等概率收集位所需到访次数的期望（集券问题）= n × H(n)，H(25) = Σ 1/k (k = 1…25) ≈ 3.81596，期望 ≈ **95.4 次到访**。

到访速率按 `docs/ECONOMY_M1.md` 第三节同一组提案参数：4 个车位（3 私家 + 1 爱心），每车位平均循环 480 分钟（无侧边帐）/ 465 分钟（侧边帐常驻展开）：

| 情形 | 每天到访 | 期望集齐天数 |
|---|---|---|
| 无侧边帐 | 4 × 1440 / 480 = 12.0 | 95.4 / 12.0 ≈ 7.95 天 |
| 侧边帐常驻展开 | 4 × 1440 / 465 ≈ 12.39 | 95.4 / 12.39 ≈ 7.70 天 |

这是期望值，最后几款等待最久（集齐最后 1 款平均还要 25 次到访 ≈ 2 天）。测试里种子 3 回放 120 天全部点亮（含开局默认车的“开过”）。

## 待讨论（不自行改值）

- **换车即点亮让完成度失去收集意义**：车库换车免费、无限制，玩家把 25 款各换一次即可 25 / 25。这是 issue #31 的明文要求，本 PR 照做；面板把“你开过”与“到访次数”分开显示，后续若要让完成度只算露营者到访，或把两者分成两个完成度，需在 #21 讨论后由用户拍板。
- 期望集齐天数（约 8 天）是否合适，取决于 NPC 参数（均为提案值，见 `src/shared/config.ts`），**待 Muse / GPT 评审**。
